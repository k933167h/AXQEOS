AX QE OS v4.9 운영 Runbook

초보자용 · GitHub: 공식 저장소 · 기준: 개발 브랜치 통합 전

설치테스트승인장애 대응증빙

1. 설치 및 설정

Docker와 Docker Compose를 설치하고 저장소를 복제합니다. .env.example을 .env로 복사한 뒤 AX_REPORTER_TOKEN, AX_SME_TOKEN, GRAFANA_ADMIN_PASSWORD에 충분히 긴 서로 다른 값을 입력합니다. 비밀키는 Git에 올리지 마세요.

git clone https://github.com/k933167h/AXQEOS.git
cd AXQEOS
cp .env.example .env
# .env 파일을 편집한 후
docker compose up --build -d
curl http://127.0.0.1:8080/health

환경 변수와 외부 API 연결이 없는 상태에서는 외부 전송이 실패할 수 있습니다.

2. Reporter 사용

테스트 도구는 /api/v1/reporter에 JSON 결과를 전송합니다. 필수 항목은 external_run_id, test_id, risk이며 인증 헤더 X-AX-Reporter-Token을 사용합니다.

curl -X POST http://127.0.0.1:8080/api/v1/reporter \
 -H 'Content-Type: application/json' \
 -H 'X-AX-Reporter-Token: YOUR_REPORTER_TOKEN' \
 -d '{"external_run_id":"demo-1","test_id":"demo","risk":0.2,"assertion_passed":false}'

TesterArmy 실제 브라우저 실행은 별도 도구 설치와 검증이 필요합니다. reporter/testerarmy.spec.ts는 연동 예제이며 운영 검증 완료본이 아닙니다.

3. 전문가 승인

검토(review) 결과만 SME 승인을 받을 수 있습니다. 승인 API와 Golden 승격 API는 별개이며 X-AX-SME-Token이 필요합니다. 공유 토큰 방식은 운영 도입 전 사용자별 인증으로 강화해야 합니다.

4. 장애 대응

API 상태: /health · 지표: /metrics · 컨테이너 로그: docker compose logs api worker. 외부 전송 실패는 SQLite outbox에 기록되며 최대 6회 시도 후 dead 상태로 전환됩니다. 자동 재처리 기능은 아직 확인되지 않았습니다.

5. 검증 및 감사

개발자 테스트: python -m pytest -q. 실행 결과, 승인 기록, Golden 승격 기록을 보존합니다. 개인정보나 환자 데이터를 공개 저장소 또는 테스트 증빙에 넣지 마세요.

현재 구현 상태와 향후 ScientistTwo 확장 계획은 Architecture Overview를 참조하세요.

6. CI 자동 검증과 증빙 확인

GitHub 저장소의 Actions 탭에서 AXQEOS CI를 열고 가장 최근 실행 결과를 확인합니다. Artifacts 영역의 axqeos-pytest-evidence에는 pytest-junit.xml과 pytest-console.log가 포함됩니다. 테스트 실패 시 로그의 첫 번째 오류를 확인한 후 수정 브랜치에서 재실행하세요. 이 CI는 API 단위 통합 테스트이며 실제 TesterArmy 브라우저와 외부 서비스까지 검증하지는 않습니다.

7. 가설 → 실험 → 전문가 심사 (개발 기능)

먼저 Reporter로 테스트 실행 결과를 등록하여 run_id를 확보합니다. SME 토큰으로 POST /api/v1/scientist/hypotheses에 source_run_id, statement, proposed_test를 전송합니다. 다음 POST /api/v1/scientist/experiments에 hypothesis_id, test_run_id, evidence_uri를 등록합니다. 마지막으로 POST /api/v1/scientist/reviews에 hypothesis_id, experiment_id, reviewer, decision(accept/reject/revise)을 입력합니다. GET /api/v1/scientist/hypotheses/{hypothesis_id}에서 기록을 확인합니다.

주의: 이 단계는 사람이 가설과 실험 결과를 등록하는 기능입니다. 자동 가설 생성·실험 실행·독립 심사·Golden 승격은 구현되지 않았습니다. SME 토큰을 공개하지 마세요.

8. 자체 품질 알고리즘 (개발자 기능)

app/quality_algorithms.py는 SHA-256 증빙 변경 탐지, 위험군별 결정적 표본 추출, 대응 지표 차이 계산, 독립 심사자 합의 확인 기능을 제공합니다. python -m pytest -q tests/test_quality_algorithms.py로 검증하세요.

주의: 현재는 독립 라이브러리이며 실제 평가 오케스트레이터에 자동 연결되지 않습니다. 증빙 해시는 출처 신뢰성을 증명하지 않으며, Ablation 차이는 인과관계를 증명하지 않습니다. Golden 승격에는 별도 SME 승인이 필요합니다.

9. 품질 알고리즘 API 사용

SME 토큰을 X-AX-SME-Token 헤더로 전달합니다. POST /api/v1/quality/evidence/verify는 run_id와 evidence, 선택적 expected_sha256을 받습니다. 기준 해시가 없으면 verified=false이며 새 해시만 계산합니다. POST /api/v1/quality/subset은 samples, fraction, minimum, seed를 사용합니다. POST /api/v1/quality/ablation은 baseline과 variant를 비교합니다. POST /api/v1/quality/reviews/consensus는 run_id와 verdicts를 입력합니다. GET /api/v1/quality/audits/{run_id}로 증빙 및 심사 기록을 조회할 수 있습니다.

이 기능은 개발 단계입니다. 심사자 ID의 실제 독립성, 기준 해시의 신뢰 출처, Ablation 인과성은 보장하지 않습니다. Golden Dataset 자동 승격은 하지 않습니다.

10. Adaptive Evaluation Routing v1

POST /api/v1/e2e/runs에 test_id, risk, assertion_passed, confidence를 전달하면 T0~T3 라우팅 결과를 받습니다. 선택적으로 evidence 객체와 expected_sha256을 함께 전달하면 해시 불일치 시 T3 검토로 전환합니다. estimated_judge_cost_usd가 config/routing.yaml의 예산을 초과하면 자동 평가를 보류합니다.

주의: 이 엔드포인트의 T1/T2는 평가 경로 추천이며 실제 모델 호출이 아닙니다. 실제 Judge 호출은 Reporter 경로에 별도 구현되어 있습니다. 비용은 예상치이고 실제 청구액이 아닙니다.
